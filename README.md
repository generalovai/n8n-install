# Установщик n8n одной командой

Ставит на чистый VPS (Ubuntu/Debian) полный рабочий n8n: **Docker + PostgreSQL + Caddy с автоматическим HTTPS**.
Всё на русском, все вопросы задаёт сам. Отдельно продуман сценарий «сервер в России».

## Команда для зрителей

```bash
curl -sSL https://raw.githubusercontent.com/generalovai/n8n-install/main/install.sh -o n8n-install.sh && bash n8n-install.sh
```

**Если `Could not resolve host: raw.githubusercontent.com`** — у части российских провайдеров
GitHub не открывается. Запасное зеркало с тем же файлом:

```bash
curl -sSL https://cdn.jsdelivr.net/gh/generalovai/n8n-install@main/install.sh -o n8n-install.sh && bash n8n-install.sh
```

Готовые воркфлоу скрипт тоже качает сначала с GitHub, потом с этого зеркала.

> Команда намеренно в два шага. Красивая форма `bash <(curl ...)` **ломается под `sudo`**:
> sudo закрывает файловые дескрипторы, и подставленный `/dev/fd/63` исчезает — проверено
> на живом сервере. А `curl ... | bash` лишает скрипт возможности задавать вопросы.
> Скачать файл и запустить — единственный вариант, который работает везде.

## Гид для зрителей

Рядом лежит [guide.html](guide.html) — обычная HTML-страница, открывается двойным кликом,
можно залить на любой хостинг. Зритель вводит домен и IP — все команды и DNS-записи
на странице подставляются под него. Внутри: сравнение трёх провайдеров (Beget, netcup,
justhost) с ценами, две ветки настройки DNS, шаг про прокси и разбор шести типовых проблем.

## Что нужно зрителю заранее

1. **Сервер.** 2 ядра и 4 ГБ памяти. На 2 ГБ n8n ставится, но потом падает по памяти — скрипт об этом предупредит.
2. **Домен.** Любой самый дешёвый — на reg.ru зона `.ru` около 200 руб/год. Бесплатных адресов больше нет: они упираются в общий лимит сертификатов и подводят.
3. **Прокси** — только если сервер в РФ и нужны зарубежные сервисы.

**Самая дешёвая связка для видео:** домен покупается на reg.ru (~200 руб), а DNS бесплатно делегируется в Cloudflare (в reg.ru меняются NS-серверы). Дальше скрипт по API сам создаёт A-запись и берёт сертификат — зрителю вообще не надо руками лезть в DNS.

## Три вопроса, которые задаёт скрипт

1. **Адрес для n8n** — `n8n.мойсайт.ru`.
2. **Прокси** — нужен или нет, и его адрес (`http://…` или `socks5://…`). Скрипт сразу проверяет, что через него есть интернет.
3. **Домен на Cloudflare?**
   - **Да** → просит API-токен, сам находит зону, сам создаёт/обновляет A-запись, сертификат берёт **через DNS** — работает, даже если провайдер закрыл 80 порт. Отдельно спрашивает про оранжевое облако.
   - **Нет** (reg.ru и любые другие) → показывает, какую именно A-запись создать, ждёт и проверяет её через `dig`, сертификат берёт по HTTP.

Дальше почта и часовой пояс — и всё.

## Как устроен прокси для РФ

Это главное отличие от типовых установщиков. Прокси нужен **в трёх местах**, иначе сценарий разваливается:

| Где | Зачем | Как сделано |
|---|---|---|
| Демон Docker | Иначе образы просто не скачаются | drop-in `/etc/systemd/system/docker.service.d/http-proxy.conf` **до** первого `pull` |
| Контейнер n8n | Чтобы ноды ходили в OpenAI, Telegram и т.п. | `HTTP_PROXY`/`HTTPS_PROXY` + строчные варианты + `NO_PROXY` + `NODE_USE_ENV_PROXY=1` + `npm_config_proxy` |
| Сборка образов | Go и Docker Hub из РФ могут не открыться | прокси прокидывается в сборку |

Две детали, которые выяснились экспериментально, а не из документации:

- **`NODE_USE_ENV_PROXY=1` обязателен.** В образе n8n Node 24, и его встроенный `fetch` по умолчанию **игнорирует** прокси-переменные. Проверено напрямую: с флагом запрос через заведомо битый прокси падает (`ECONNREFUSED`), без флага — спокойно уходит в интернет мимо прокси. Без этой строки половина нод на РФ-сервере молча ходила бы напрямую и не работала.
- **socks5 нужен мост.** Ни n8n, ни Docker не умеют socks5 для контейнеров. Если зритель вводит `socks5://…`, скрипт поднимает крошечный контейнер-мост (tinyproxy, 14 МБ): принимает HTTP, отдаёт в socks5. Демону Docker socks5 скармливается напрямую через `ALL_PROXY` — он это умеет.

В конце установки скрипт **сам проверяет** прокси: делает запрос из контейнера n8n и показывает, с какого адреса n8n вышел наружу. Если адрес совпал с адресом сервера — честно пишет, что прокси не применился.

## Что делает по шагам

| Шаг | Что |
|---|---|
| 0 | ОС, архитектура, диск, внешний IP; проверка железа — при меньше 2 ядер или 4 ГБ предупреждает и спрашивает подтверждение |
| 1 | Домен |
| 2 | Прокси: ввод, проверка живости, выбор http/socks5 |
| 3 | Cloudflare (токен → зона → A-запись → облако) либо A-запись руками с проверкой `dig` |
| 4 | Почта и часовой пояс |
| 5 | Ключ шифрования и пароли Postgres |
| 6 | Docker + прокси демона |
| 8 | Swap 2 ГБ (если RAM < 4 ГБ), unattended-upgrades, ufw (80/443 + реальный порт SSH) |
| 8 | `/opt/n8n`: compose, Caddyfile, `.env` (600), `backup.sh`, `update.sh`, `restore.sh`, `autoupdate.sh`, ночные cron |
| 9 | Сборка нужных образов, запуск, ожидание `/healthz`, ожидание сертификата, проверка прокси |

В конце крупно выводит ключ шифрования с предупреждением.

## Перезапуск

Скрипт идемпотентен:

- ключ шифрования, пароли БД, домен, токен Cloudflare и прокси **читаются из `.env`** и переиспользуются;
- Docker, swap, unattended-upgrades, правила ufw, cron ставятся только если их ещё нет;
- `docker compose up -d` пересоздаёт только изменившееся, тома с данными не трогаются;
- при любой ошибке — причина по-русски и «запустите ту же команду ещё раз».

## Режим «всё включено»

- `N8N_COMMUNITY_PACKAGES_ENABLED` + `N8N_COMMUNITY_PACKAGES_ALLOW_TOOL_USAGE` — community-ноды, в том числе как инструменты AI-агентов
- `N8N_UNVERIFIED_PACKAGES_ENABLED`, `N8N_VERIFIED_PACKAGES_ENABLED`, `N8N_COMMUNITY_PACKAGES_PREVENT_LOADING=false`, `N8N_REINSTALL_MISSING_PACKAGES`
- `N8N_PYTHON_ENABLED=true` — Python в Code-ноде
- `NODES_EXCLUDE=[]` — ни одна нода не заблокирована, включая Execute Command
- `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` — `$env` доступен из нод
- `NODE_FUNCTION_ALLOW_BUILTIN=*`, `NODE_FUNCTION_ALLOW_EXTERNAL=*`
- `N8N_BLOCK_FILE_ACCESS_TO_N8N_FILES=false`
- `EXECUTIONS_TIMEOUT=-1`, `N8N_CONCURRENCY_PRODUCTION_LIMIT=-1`, `N8N_PAYLOAD_SIZE_MAX=1024` МБ, `request_body max_size 1GB` в Caddy
- `N8N_RUNNERS_TASK_TIMEOUT=3600`, распаковка 2 ГиБ, 5000 записей в zip — n8n предупреждает, что срежет эти дефолты в будущих версиях, поэтому фиксируем большие явно
- `NODE_OPTIONS=--max-old-space-size` — 60% RAM сервера
- телеметрия и персонализация выключены

Две оговорки:

1. Отдельной переменной «показать deprecated/скрытые ноды» в n8n нет. Реально прячет ноды список `NODES_EXCLUDE` (по умолчанию там Execute Command и Local File Trigger) — мы делаем его пустым. ([docs](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/nodes))
2. `NODE_FUNCTION_ALLOW_EXTERNAL=*` разрешает внешние модули, но не устанавливает их — модуль должен быть в контейнере.

## Оранжевое облако Cloudflare

По умолчанию выключено, и скрипт объясняет почему: на бесплатном тарифе через него не пройдут файлы больше 100 МБ. Если зритель всё же включает, скрипт делает три вещи, без которых оно работает криво:

- `N8N_PROXY_HOPS=2` — прокси теперь два (Cloudflare + Caddy), иначе n8n видит не тот IP клиента;
- в Caddy прописываются `trusted_proxies` со списком сетей Cloudflare (скачивается с их сайта) и `client_ip_headers CF-Connecting-IP`;
- `N8N_PUSH_BACKEND=websocket` — вебсокеты через Cloudflare работают надёжнее, чем SSE.

## Безопасность

- Наружу торчит только Caddy (80/443). Порты 5678 и 5432 не публикуются.
- `.env` с ключом, паролями и токеном Cloudflare — `chmod 600`, только root.
- Токен Cloudflare вводится скрыто и просится по шаблону **Edit zone DNS** — прав только на записи DNS одного домена.
- Ключ шифрования генерируется на самом сервере.
- Режим «всё включено» намеренно снимает часть штатных ограничений n8n. Это нормально для личного сервера одного владельца — но не пускайте в такой n8n посторонних.

## Автообновление

Скрипт спрашивает при установке (по умолчанию — включить). Ночью в 03:00 `autoupdate.sh`:
проверяет, вышла ли новая версия → если нет, молча выходит → если да, делает копию,
обновляет и ждёт `/healthz/readiness`.

**Если новая версия не поднялась**, он сам: возвращает прежний образ (локальный тег
`rollback`, без сети), проверяет снова; если и это не помогло — восстанавливает базу
из копии, сделанной перед обновлением. В конце пишет `ОБНОВЛЕНИЕ-НЕ-УДАЛОСЬ.txt`
с человеческим объяснением и **ставит автообновление на паузу**, чтобы оно не билось
в ту же ошибку каждую ночь.

Проверено живьём на Linux: подсунут заведомо сломанный образ — откат отработал,
данные целы, n8n поднялся, файл-предупреждение создан, следующий запуск не повторил попытку.

`update.sh` — та же логика с `--force`, для ручного запуска.

## Уведомления в Telegram

Настраиваются при установке (по желанию). Токен от @BotFather, а **свой chat id искать
не нужно** — скрипт просит написать боту и вылавливает отправителя через `getUpdates`.
Дальше проверяет токен через `getMe` и шлёт тестовое сообщение.

Пишет только по делу, без ежедневного шума:

| Событие | Кто отправляет |
|---|---|
| Установка завершена (адрес + ключ шифрования) | `install.sh` |
| Обновились: версия X → Y | `autoupdate.sh` |
| Обновление не удалось, вернули прежнюю версию | `autoupdate.sh` |
| Не сделалась резервная копия | `backup.sh` |
| Диск занят на 85% и больше | `backup.sh` |
| n8n перестал отвечать / снова работает | `watch.sh`, cron каждые 10 минут |

Сторож хранит состояние в `.watch-state` и сообщает **только при изменении** — лежачий
сервер не будет слать сообщение каждые 10 минут. Проверено живьём: healthy → тишина,
падение → одно сообщение, ещё проверка → тишина, восстановление → одно сообщение.

Честное ограничение: если умрёт сам сервер целиком, отправлять сообщение будет некому.
Для этого нужен внешний монитор вроде UptimeRobot.

## Внешний сторож (UptimeRobot)

Наши уведомления живут на том же сервере, поэтому его полную смерть заметить не могут.
В гиде есть раздел с точными шагами: бесплатный монитор HTTP(s) на
`https://домен/healthz`, интервал 5 минут (максимум бесплатного тарифа, 50 мониторов).
`/healthz` отдаёт `{"status":"ok"}` без авторизации — идеальная цель для проверки,
и она разом покрывает домен, сертификат, Caddy и сам n8n.

**Почему инструкцией, а не автоматикой через их API:** создать монитор в интерфейсе —
это 4 клика, а получить API-ключ — примерно столько же действий. Зато интеграция
с чужим API (v2 у них объявлен legacy, v3 ещё меняется) — это ровно тот код, который
однажды молча сломается у всех подписчиков сразу, и вы узнаете об этом из комментариев.
Меньше движущихся частей — меньше того, что чинить.

## Как это сопровождать дальше

Три вопроса, которые возникнут: как не сломать при правках, как узнать о поломке
у подписчика, как раскатить исправление.

**Не сломать при правках.** Все проверки лежат в репозитории и запускаются одной командой:

```bash
tests/run.sh
```

Она делает синтаксис, shellcheck по установщику и всем восьми генерируемым скриптам,
восемь сценариев установки в чистой Ubuntu и валидацию compose с Caddyfile в обоих режимах.
То же самое гоняется автоматически на каждый push — `.github/workflows/ci.yml`.
Если правка что-то ломает, вы узнаете до того, как это увидит зритель.

**Узнать о поломке у подписчика.** Вместо расспросов — одна команда:

```bash
/opt/n8n/diagnose.sh
```

Собирает отчёт: версия установщика, состояние контейнеров, версия n8n, ответ изнутри
и снаружи, сертификат, свежие ошибки из логов n8n и Caddy, история обновлений и сторожа,
список копий, задания в cron. **Пароли, ключи и токены в отчёт не попадают** — есть
и явные исключения, и финальная зачистка по маске. Файл можно спокойно переслать.

**Раскатить исправление.** Все вспомогательные скрипты на сервере перезаписываются
при каждом запуске установщика, а секреты, домен и настройки читаются из `.env`.
Поэтому обновление у подписчика — это та же самая команда установки, что и в первый раз:
данные не тронутся, скрипты обновятся. В `.env` пишется `INSTALLER_VERSION`, и при
повторном запуске скрипт сообщает: «обновляем установку с версии X до Y».

**Понять, что уведомления вообще живы.** Молчащий канал не отличить от сломанного,
поэтому первого числа каждого месяца приходит короткая сводка: адрес, версия, занятость
диска, число копий. Перестала приходить — значит что-то сломалось в самих уведомлениях.

## Про время ночных работ

Задания идут по системному времени сервера, а на VPS это почти всегда UTC — то есть
«2:00» означало бы 5 утра по Москве. Поэтому установщик **переводит часовой пояс сервера
на тот, который человек выбрал**, и перезапускает cron (иначе тот остался бы на старом).
Дальше «2:00» — это 2:00 у владельца.

Порядок специально такой: **02:00 копия → 03:00 обновление**. Данные были бы защищены
и наоборот (`autoupdate.sh` делает свою копию прямо перед тем, как что-то трогать),
но так расписание читается по-человечески.

## День 2

```bash
/opt/n8n/update.sh     # обновление (сначала делает бэкап, при Cloudflare пересобирает Caddy)
/opt/n8n/backup.sh     # бэкап вручную
/opt/n8n/restore.sh    # без аргументов - покажет список копий
/opt/n8n/restore.sh 2026-08-07_03-30
```

`restore.sh` перед восстановлением сам подставляет в `.env` ключ шифрования из копии — иначе доступы не расшифруются. Это главная ловушка ручного восстановления.

Бэкап = дамп Postgres + том `n8n_data` + копия `.env`. Хранятся последние 14, ночной cron в 03:30, лежат в `/opt/n8n/backups`. Копии остаются на том же сервере — скажите зрителям скачивать их к себе.

## Найденные и исправленные баги

Все — из прогонов, ни один не был бы виден при чтении кода.

1. Бесконечный цикл вопросов, если терминал недоступен.
2. `umask 077` делал `init-data.sh` нечитаемым для uid postgres — пользователь БД не создавался бы.
3. Определение SSH-порта падало на Ubuntu 24.04 (sshd на systemd-сокете) и роняло весь установщик.
4. `WEBHOOK_URL` и `N8N_RUNNERS_ENABLED` устарели в n8n 2.x; `N8N_VERIFY_COMMUNITY_PACKAGE_CHECKSUM` не существует.
5. `trusted_proxies` — не директива сайта; перенесена в глобальный блок `servers`.
6. tinyproxy не разбирает `upstream socks5 host:port` без `"*"` — мост молча отдавал 502.
7. Пароль прокси с `@` ломает конфиг моста — теперь предупреждение на вводе.
8. **`restore.sh` сносил базу до проверки копии** — битый архив означал потерю данных без возврата. Теперь копия сначала проверяется (`gunzip -t`, `tar tzf`), а перед заменой снимается страховочный дамп текущего состояния.
9. Не было `--remove-orphans` — после смены socks5-прокси на обычный мост оставался висеть лишним контейнером.
10. Логи контейнеров ничем не ограничены — за месяцы забили бы диск. Добавлены лимиты (10 МБ × 3) и logrotate для логов установщика и бэкапа.
11. `docker compose pull` пытался скачать из реестра локально собираемые образы и падал — и в `install.sh`, и в `update.sh` (там чинится через `--ignore-buildable` с запасным путём для старых версий).
12. **Пароль прокси с одним `$` Docker Compose съедал молча**: `pa$w0rd` превращался в `pa`, прокси не авторизовывался без единой подсказки. Теперь в `.env` пишется `$$`, при чтении разворачивается обратно (проверено и на повторном запуске — двойного экранирования нет).
13. Поиск зоны Cloudflare тянул список всех зон с `per_page=200`, хотя лимит страницы не гарантирован. Заменено на точечные запросы по имени для каждого варианта домена.
14. У записи за оранжевым облаком TTL теперь `1` («автоматически») — Cloudflare не любит произвольный TTL у проксируемых записей.
15. Для домена без поддомена инструкция показывала имя `mysite` вместо `@`.
16. Для socks5 в проверках используется `socks5h`, чтобы имена резолвил прокси, а не сервер с возможно подменённым DNS.
17. Живость прокси проверялась через `api.telegram.org` — заменено на нейтральный `api.ipify.org` с запасным адресом, чтобы не забраковать рабочий прокси.

## Что осталось на реальный VPS

Локально это проверить нельзя:

- выдача настоящего сертификата — обоими способами (HTTP-01 и DNS-01 с живым токеном Cloudflare);
- установка Docker с нуля (`get.docker.com`);
- работа через настоящий российский прокси и скачивание образов через него;
- `ufw --force enable` по живому SSH-соединению;
- реальное поведение оранжевого облака (вебсокеты редактора, лимит 100 МБ).
